## 1. Where the Group A build differs from the spec

Recorded as built, per `CLAUDE.md` ("when the design and the code must diverge, update the
design document").

| # | Item | Spec says | What we did and why |
| --- | --- | --- | --- |
| A1 | P1a-01 | `users.status` (values not given) | `invited`, `active`, `deactivated`. `invited` is a user created by an operator or admin who has not signed in yet; the first successful sign-in makes them `active` (P1a-02). Only `active` users of `active` tenants pass authentication. |
| A2 | P1a-01 | `tenants.status` (values not given) | `active`, `suspended`. Termination and its purge cascade (architecture §7.4) are not in Phase 1a. |
| A3 | P1a-01 | `tenant_entitlements(tenant_id, answer_modes[], …)` | Also `updated_at`. `answer_modes` is checked against the Phase 1a modes (`corpus_only`, `general_knowledge`) and must contain `corpus_only`; web search (Phase 2) widens the check in its own migration. |
| A4 | P1a-01 | "Phase 0's hard-coded tenant becomes a row" | It was already a row (revision 0001 seeded `internal`). What was hard-coded was the request context: the Phase 0 middleware set `INTERNAL_TENANT_ID` itself. Now both auth modes resolve the context from the user's row, looked up inside the tenant the credential names (`app.tenancy.context.resolve_user`), and a route without a context returns 401 before opening a transaction. The Phase 0 bearer token still admits only active users of the internal tenant. |
| A5 | P1a-01 | (stub) | **Stub until P1a-04.** The package is still Phase 0's (every tag in `config/tags.toml`), and only the internal tenant gets it (`app.chat.package.tenant_package_tags`). A client tenant created by the operator before its workspaces exist retrieves nothing and abstains, rather than inheriting our corpus. P1a-04 replaces the stub with the workspace's tags. |
| A6 | P1a-02 | "Only the button's POST submits the token to the Authentik flow"; "the API validates Authentik's OIDC tokens" | The button POSTs to our API (`POST /api/v1/auth/link/complete`), which checks binding, single use and expiry and only then submits the token to Authentik's flow executor, server-side. Browsers never hold an Authentik session and Authentik publishes no port. The API runs the authorization-code flow with PKCE in that server-side session and sets the Authentik **access token** as an HttpOnly, Secure, SameSite=Strict `askspore_session` cookie; every request is validated against Authentik's JWKS (RS256/ES256 only, issuer, audience, expiry). A `Bearer` header is accepted too (scripts). |
| A7 | P1a-02 | Authentik email-link stage with browser binding | **Desk-checked, not run live.** Read against the authentik `version-2026.8` source (pinned `2026.8.4`): a flow token restores its plan in any browser, so Authentik does **not** bind links to the requesting browser; it does put a one-time consent stage in front and deletes the token only when that is answered, not on GET. The API therefore enforces binding itself: `POST /auth/link` sets a random binding cookie, only its SHA-256 is stored (`sign_in_links`), and completion without it is refused before anything reaches Authentik. The adapter (`app.auth.authentik`) is tested against a simulated Authentik only; the flow, provider and scope mapping are configured by hand (`infra/authentik/README.md`, no blueprint yet). The email template's link host is a placeholder replaced at deploy. |
| A8 | P1a-02 | "maps the identity to a `users` row by tenant and email" | The tenant comes from the token's `ask_spore_tenant` claim, which Authentik copies from the user attribute the operator console sets when it provisions the user; the row is then looked up by (tenant, email) under that tenant's RLS scope, so no request-time query crosses tenants. A link request names only an email, so the pre-authentication lookup runs as a separate NOLOGIN role `askspore_auth` that the app role may `SET ROLE` to but does not inherit, reading only status, email and the links entitlement (revision 0005). Authentik usernames are emails, so an email belongs to one tenant; the operator console refuses to invite an email that exists in another tenant (P1a-03). |
| A9 | P1a-02 | "Auth success and failure write `audit_events`" | Link requests, rate-limit refusals, sign-ins and failed completions are audited with `method = sign_in_link`. Failures that cannot be attributed to a tenant (no binding cookie, unknown binding) are audited under the internal tenant, our platform tenant; per-request token rejections (expired session and so on) are logged with an error code, not audited, so the audit log is not flooded. |
| A10 | P1a-02 | Rate limits per address and per IP (architecture §8) | Per user: at most `links_per_window` (5) links per link lifetime; further requests send nothing and are audited `auth.link_refused`. Per IP: not in the API; left to the proxy (backlog). |
| A11 | P1a-02 | Phase 0 bearer token replaced | Kept behind `[auth] mode = "phase0"` in `config/models.toml` for the eval harness; `mode = "oidc"` uses Authentik. Only the active mode's secrets are required at startup, and in `oidc` mode a leftover `PHASE0_BEARER_TOKEN` is ignored. The eval harness still needs `phase0` until it gets an OIDC path. |
| A12 | P1a-03 | "Operator role lives outside tenant RLS and is checked by a separate dependency" | An operator is an active user of the internal (platform) tenant listed in `operators`, signed in through Authentik; the Phase 0 bearer token never reaches the console. `app.operator.deps.require_operator` checks this without any tenant role, and operator routes then run as the NOLOGIN role `askspore_operator` (`SET LOCAL ROLE`; the app role may assume it but does not inherit it), whose policies see every tenant but whose privileges cover only tenants, users (create), entitlements, notices and audit events: it cannot read conversations, messages, citations, feedback, sign-in links or sources (revision 0006, tested). Operators are granted and revoked only from the command line as the schema owner (`ask-spore operators grant --email … [--name …]`), audited under the internal tenant. Hardware-key MFA for operators (architecture §4.3) is Authentik configuration and is not checked by the API (open question). |
| A13 | P1a-03 | Enabling external models requires an acceptance reference stored on the entitlement and in the audit event | `tenant_entitlements.external_acceptance_reference` and `external_acceptance_date`; the route refuses (422 `acceptance_required`) to switch external models on without both, and also without a spend cap (`spend_cap_required`) or with a future date. A check constraint refuses `external_models_enabled` without reference, date and cap whoever writes. The audit event carries `acceptance_reference` and `acceptance_date` besides before and after. The acceptance stays on file when the switch is turned off. The P1a-15 gate ("not enabled for any tenant until P1a-15 is done") is a process rule; no code enforces it. |
| A14 | P1a-03 | "enabled models" | **Stub until P1a-09.** Without the `[catalogue]`, the only model that can be enabled is the active provider's chat model (`app.tenancy.entitlements.available_models`); new tenants get it by default. The external-models switch can be set (with the acceptance) but no external model can be enabled until P1a-09 lists them. |
| A15 | P1a-03 | "invite first admin" | Creates the `users` row (`tenant_admin`, `invited`) and provisions the Authentik user with the tenant attribute, in one transaction (rolled back if Authentik refuses). No email is sent by the invitation: links are bound to the browser that asks for one, so the admin requests their first link on the sign-in page. Audit rows name the user ID, not the email. Operator changes are audited under the affected tenant with `actor_user_id` empty and `operator_id` in the metadata, since the operator is not a user of that tenant. |
| A16 | P1a-03 | "operator notices list (fed by P1a-07 and P1a-10)" | Table `operator_notices` (tenant-scoped, forced RLS) and the list route. Nothing writes notices yet; the application role gets INSERT in the migrations of P1a-07 and P1a-10, not before. A domain belongs to one tenant: checked by the create route under the operator role (no database constraint on array overlap). |

## 2. Where the Group C build differs from the spec

Group C (P1a-09 to P1a-11), Oct 19, 2026. Built in parallel with Group B, which owns the
conversation and message columns (`model`, `reasoning`), the cache key and the
orchestrator's retrieval and prompt path; the integration points are named in each row.

| # | Item | Spec says | What we did and why |
| --- | --- | --- | --- |
| C1 | P1a-09, P1a-10 | "fall back to the workspace default model" | **Stub until P1a-04 merges.** There is no workspace default yet, so the stand-in is `app.tenancy.entitlements.tenant_default_choice`: the platform default model (`[scaleway] chat_model`) when the tenant has it enabled, otherwise the tenant's first enabled EU model in catalogue order, reasoning off. It is never an external model (`enabled_models` is sorted, so "first enabled" alone would pick `anthropic/…`, which would make the spend-cap fallback external). `app.chat.selection.conversation_choice` reads `conversations.model` and `reasoning` once the ORM model has them and falls back to this default until then. After the merge, the workspace's `default_model` and `default_reasoning` replace it, provided they pass the same check. |
| C2 | P1a-09 | `api.openrouter.ai` joins `external_hosts` | Done as given. OpenRouter's published endpoint is `https://openrouter.ai/api/v1`; whether `api.openrouter.ai` serves the API was not checkable from the build container (no outbound DNS). `[openrouter] base_url` is `https://api.openrouter.ai/api/v1`. The owner confirms host and path when the account is opened; a change is a one-line config edit plus the allow-list entry. |
| C3 | P1a-10 | Pinned slugs `openai/gpt-6.1-sol`, `anthropic/claude-opus-5.5` | In `[openrouter] models` and the catalogue only; no code names them. Not confirmed by the owner (open item of the spec). The startup check accepts only `vendor/model` slugs: no `-latest`, no `:variant` suffix (`:online` would add OpenRouter's web-search plugin, `:free` changes upstream terms) and no `openrouter/…` meta-router. |
| C4 | P1a-09 | "price per million tokens in and out" | `price_in_cents_per_mtok` and `price_out_cents_per_mtok`, in **euro** cents, the unit of `external_spend_cap_cents`. The figures in the repository are **provisional placeholders**; they must be replaced from Scaleway's and OpenRouter's price lists before any tenant is capped on them (OpenRouter bills in USD: the owner sets the euro figure, with any margin). |
| C5 | P1a-09 | "Add `qwen3.8-27b` to the Scaleway section" | `[scaleway] models = ["deepseek-v4.1-flash", "qwen3.8-27b"]`, the Scaleway names the catalogue may offer, fixed-name checked like the other Scaleway names; `[openrouter] models` likewise. Startup also refuses a catalogue entry its provider section does not pin, an `external` flag that does not match the provider (OpenRouter external, Scaleway and Mistral not), a reasoning switch the provider does not offer, a duplicate entry, and a catalogue without the active provider's chat and rewrite models. A host on both allow-lists, an EU service on an external host and OpenRouter on an EU-listed host are refused. |
| C6 | P1a-09 | Users see that external models are served outside the EU (compliance addendum) | New route `GET /api/v1/models`: the models the signed-in user may pick (enabled for the tenant; external ones only with the entitlement), each with `display_name`, `external`, `reasoning_switch` and `default`. The picker itself is Group D (P1a-12). |
| C7 | P1a-10 | (not stated) | `OPENROUTER_API_KEY` is optional. Without it no OpenRouter client exists and every external model is refused as `model_unavailable` before any call, so an Instance can run before the OpenRouter account and paperwork (P1a-15) exist. |
| C8 | P1a-09 | "The orchestrator refuses … before any outbound call" | The check (`app.chat.selection.authorize`) runs in the orchestrator's first tenant transaction, before the query rewrite (an outbound call to Scaleway), retrieval and generation. A refusal is an `error` event with the code (`model_unavailable`, `model_not_enabled`, `external_not_entitled`, `reasoning_unsupported`, and from P1a-10 `spend_cap_reached`) and a `chat.query` audit row naming the refused model. |
| C9 | P1a-10, P1a-11 | "DeepSeek and Qwen thinking enabled or disabled; GPT and Claude reasoning effort medium or none" | `app.llm.reasoning`. Switch `thinking` (Scaleway): off sends `reasoning_effort: "none"` (checked live for DeepSeek, findings M2); on sends nothing and leaves the model's default, which for DeepSeek on Scaleway is to think (M2). **Not checked live for `qwen3.8-27b`**: confirm on the account that Qwen thinks by default and accepts `reasoning_effort: "none"`; if not, the switch needs a provider-specific field (for example `chat_template_kwargs.enable_thinking`) and a new switch kind. Switch `effort` (OpenRouter): `reasoning: {effort: "medium" or "none", exclude: true}`; `exclude` asks OpenRouter not to return reasoning text at all. Answers keep temperature 0.2 for every model; OpenRouter drops parameters a model does not support unless told otherwise. |
| C10 | P1a-10 | "zero-data-retention routing option set on every request, … timeouts, one retry on 5xx" | Every OpenRouter request carries `provider: {zdr: true, data_collection: "deny"}`, set last so no other field can override it (tested), and no `user` field, attribution headers (`HTTP-Referer`, `X-Title`), tools or plugins. Only pinned slugs are sent (the client refuses others before any call). Timeout `[openrouter] timeout_seconds` (90 s), SDK retries off, one retry when the stream fails to open with a 5xx, none mid-stream (as for Scaleway). No client-side throttle: OpenRouter's own limits and the spend cap bound it. |
| C11 | P1a-10 | `usage_ledger(tenant_id, month, model, tokens_in, tokens_out, cost_cents)` | As specified, plus `updated_at`; keyed `(tenant_id, month, model)` (the `tenant_id`-first index), forced RLS, application role SELECT, INSERT and UPDATE (upsert), no DELETE, no operator access yet. `month` is the first day of the UTC calendar month. `cost_cents` is `numeric(16,6)` euro cents priced from the catalogue at the time of the call, fractional so small calls do not round to zero. Every model is recorded, EU models too (exit criterion "usage and cost are recorded per tenant"); a query rewrite is recorded under the rewrite model. Only external models count towards the cap. Revision `0007` (see C14). |
| C12 | P1a-10 | "operator notice once per month at 80 percent" | Notices `spend.cap_80` and also `spend.cap_100` (the operator should know when the hard stop starts), each once per tenant and month, with month, threshold, cap and spend in the metadata. "Once" is enforced by a new tenant-scoped table `spend_notices(tenant_id, month, threshold)` (forced RLS, primary key `tenant_id`-first) written with `ON CONFLICT DO NOTHING` in the transaction that stores the message: an `ON CONFLICT` insert into `operator_notices` itself would need SELECT on it, which the application role must not have. Revision 0007 grants the application role INSERT on `operator_notices`; P1a-07 (Group B) grants the same, GRANT is idempotent, and the 0007 downgrade does not revoke it. |
| C13 | P1a-10 | "At 100 percent new conversations on external models are refused with a user-facing notice and fall back to the workspace default model" | `app.chat.selection.choose_for_new_conversation` checks the requested choice (refusing what the entitlement does not allow) and, at or above the cap, returns the default model (C1) with reasoning kept on where that model has a switch, the notice code `external_spend_cap_reached` and a short user-facing text, and audits `model.fallback` (model, reasoning, requested model). **Existing** conversations on an external model are refused with `spend_cap_reached` before any call, because a conversation's model cannot change (spec, "Not in this phase") and the compliance risk register calls the cap a hard stop. The check precedes the call and the cost is known after it, so concurrent answers can overshoot by what is in flight. A cap of 0 refuses every external call. **Integration:** P1a-04's conversation-create route must call `choose_for_new_conversation` and store its `choice`; until then no conversation can be on an external model (C1). |
| C14 | P1a-10 | (merge) | The ledger migration is revision `0007` after Group A's `0006`. Group B's migrations, merged first, will also follow `0006`: at the merge, renumber `0007_usage_ledger.py` after Group B's head (`revision` and `down_revision`) so Alembic has one head. |

## 1. Where the Group A1 build differs from the spec

Recorded as built, per `CLAUDE.md` ("when the design and the code must diverge, update the
design document"). Migrations 0013 (register states and content roles), 0014 (jobs) and 0015
(withdrawal and re-ingestion).

| # | Item | Spec says | What we did and why |
| --- | --- | --- | --- |
| A1-1 | P1b-01 | `proposed → approved → ingested → withdrawn`, plus `failed` (retryable) | Also **`rejected`**: a reviewer's "reject" (P1b-01 roles, P1b-05 "approve and reject with a note") needs an end state, and `withdrawn` means "removed from the corpus", which a rejected proposal never entered. `failed` is retried by a reviewer (`failed → approved`, `sources retry`), which enqueues a new job. The Phase 0 values go in migration 0013: `registered` becomes `proposed`, an `ingesting` row (an ingestion that never finished) becomes `failed`. Rows ingested before Phase 1b have no proposer or approver; their `approved_at` is their last update, and check constraints require an approval date on every row past `proposed`/`rejected` and a date and reason on every `withdrawn` row. |
| A1-2 | P1b-01 | Register columns listed | Also **`review_note`**: the reviewer's note on an approval or rejection (P1b-05 asks for one). The note stays on the row and is never put in the audit event, which carries status before and after, the reviewer's roles and `self_approval` only. `proposed_by` and `approved_by` have no foreign key, like `audit_events.actor_user_id`, so the register keeps its history when a user goes. `licence_file_path` is constrained to `licences/<sha256>.<ext>` under `content_root` (`app.content.store.store_licence`); uploading one is the console's (P1b-05). |
| A1-3 | P1b-01 | "Two content roles on internal-tenant users, in a new `content_roles` table" | `content_roles(tenant_id, user_id, role)`, `tenant_id` pinned to the internal tenant by a check constraint, forced RLS and a `tenant_id`-first key (it carries `tenant_id`, so the rule for tenant tables applies, as for `operators`). Granted and revoked only from the command line as the schema owner (`ask-spore content-roles grant|revoke --email … --role …`), audited, like the operator role. The application role may only read it, inside the internal tenant's scope; no grant to `askspore_operator` yet: the console pages (P1b-05) decide how they check roles. |
| A1-4 | P1b-01 | Self-approval allowed and "audited with both roles named" | Every approval audits the reviewer's roles (`roles`, sorted) and `self_approval` (true when the reviewer proposed it). The audit allow-list gains `roles` and `self_approval`. |
| A1-5 | P1b-01 | "The manifest CLI creates `proposed` rows and, with `--approve-as`, approves them" | Also **`--propose-as`** (the content editor proposing). It defaults to the `--approve-as` user, so a run of our own corpus is proposed and approved by the owner, a self-approval audited as such. Without either flag the rows are proposed with `proposed_by` empty and the audit event says `method: cli` (the operator's shell). The same flags (and `--wait`) were added to **`ask-spore ingest` and `ask-spore crawl`**: they were direct paths into RAGFlow, which "no document reaches RAGFlow before a reviewer approves" rules out. Until the console exists, a reviewer decides from the command line: `ask-spore sources approve|reject|retry|withdraw|takedown <source_id> --as <email>`. |
| A1-6 | P1b-01 | (re-tagging, P1a-04) | Linking an ingested file into more tags changes which tenants can retrieve it, so it now needs a reviewer too: with `--approve-as` it is approved (`source.retag_approved`, audited with the reviewer) and runs as an `ingest_source` job with `add_tags`; without it the row reports `retag_pending` and nothing is recorded (re-run with `--approve-as`). There is no stored "proposed re-tag". |
| A1-7 | P1b-01 | (not in the spec) | A file whose content hash matches a source **withdrawn after a takedown request** is not proposed again: the row fails with `taken_down`. Otherwise a re-run of the manifest with `--approve-as` would quietly put a taken-down document back. A plainly withdrawn or rejected file can be proposed again (a new row). |
| A1-8 | P1b-02 | Worker reads the file to upload | Every proposed file, **pages included**, is staged under `[files] content_root` by hash at proposal (`app.content.store.stage`), because the worker runs in its own container and a job's payload carries no document contents. P1a-14 said pages are never stored; they are still never downloadable (`stored_path` is set only for PDF, DOCX and PPTX). The staged copy stays after ingestion (re-tags and retries read it) and is deleted on withdrawal. The CLI no longer talks to RAGFlow for ingestion; it needs the database and the content volume only. |
| A1-9 | P1b-02 | `jobs` (type, payload, status, attempts, error_code, timestamps) | Statuses `queued`, `running`, `succeeded`, `failed`. Also `max_attempts` (3), `run_after` (backoff 1, 2, 4 … minutes, capped at an hour), `locked_until` (a 5-minute lease the worker renews while it works; a job whose worker died is claimed again when it lapses) and `created_by`. A check constraint limits the payload to the keys `source_id`, `site_id`, `add_tags`, `downloadable` and `parse_timeout` and caps its size; another limits `error_code` to a short identifier, so no error text can be stored. Only transient RAGFlow failures (timeout, unreachable, HTTP 5xx) are retried automatically; a parse failure or a refusal fails the job at once, and the source is `failed` for a reviewer to retry. A partial unique index allows one queued or running job per type and subject, so an approval enqueues exactly one job, in the approval's own transaction. SIGTERM puts the running job back without counting the attempt. |
| A1-10 | P1b-02 | `crawl_site` job type | The type exists (and `site_id` is an allowed payload key), but the handler is P1b-04's: a `crawl_site` job fails with `unsupported_job_type` until then. The manifest's `site` rows are still crawled by the CLI, and each page goes through the register and the queue like a file. |
| A1-11 | P1b-02 | "the worker does what the P0-09 CLI does today" | Plus: each upload is recorded on the row at once, so a run cut off by a stopped worker leaves a mapping the next attempt deletes from RAGFlow before uploading again. While a source is `approved` and parsing, its chunks can already be retrieved and cited, as an `ingesting` row's could before (`provenance_by_document` excludes only withdrawn sources); unchanged from Phase 1a. An interrupted **re-tag** is not cleaned up this way: its new documents are named in nothing until it succeeds (as before, findings P1a-04). |
| A1-12 | P1b-02 | "The CLI stays as a thin client that enqueues and waits" | Waiting is opt-in with **`--wait`**, so a long manifest can be queued and left to the worker. Without it rows report `proposed`, `retag_pending` or `queued`; with it the final `ingested`, `retagged`, `duplicate` or `failed` (with the job's error code). A row's time in the summary is its submit time plus its job's run time. A `retagged` row reports 0 chunks after `--wait`, because a job records status and error code only. |
| A1-13 | P1b-02 | Worker Compose service | `worker`: the api image with `ask-spore worker`, no published port, on the `app` and `ragflow` networks, with the config and content volumes and Redis (P1b-03 purge). The image's HTTP healthcheck is disabled for it (the CLI run containers of findings 1a §9 showed `unhealthy` for that reason). One job at a time keeps RAGFlow's load as in findings 1a §9 (`MAX_CONCURRENT_TASKS=2` unchanged). Log lines carry `job_id`, `job_type`, `attempts`, `status`, `error_code` (allow-list extended, tested). |
| A1-14 | P1b-03 | Re-ingestion: "new hash, same canonical link" | A proposal whose new file sits at the canonical link of **exactly one** ingested source records `supersedes_id`; once it is ingested, the old source's `withdraw_source` job is enqueued in the same transaction. When several ingested sources share the link, nothing is superseded (the file is a new source). The old row becomes `withdrawn` with the reason "superseded by a re-ingested version" (there is no `superseded` status), and its citations get `superseded_at`, not `withdrawn_at`. **Spec question below.** |
| A1-15 | P1b-03 | Withdrawal cascade | As specified, plus: only an `ingested` or `failed` source can be withdrawn (a proposal has nothing in RAGFlow; an approved one has a job in flight); and the job **deletes our stored copy of the file** unless another live source has the same content, since a takedown for a licence breach should not leave a copy on our disk either. Stored citations keep their excerpt and provenance and are labelled (spec question below). The job runs as a new NOLOGIN role **`askspore_content`** (the app role may `SET LOCAL ROLE` to it, as for `askspore_operator`), because the flags must be set in every tenant's history and the app role is tenant-scoped: it may read only `id`, `tenant_id`, `source_id` and the two flags of `citations` (never the excerpt), update only the flags, and read `tenants.id` (tested). |
| A1-16 | P1b-03 | "purge the tenant answer caches that cite it (cache entries record their source IDs from P1b-03 on)" | Cache values gain `source_ids` (no migration). The purge walks each tenant's `answer:` namespace with `SCAN` through two new `app.core.cache` helpers (`scan`, `delete`, tenant-prefixed like the rest) and deletes entries whose `source_ids`, or for values cached before P1b-03 whose citations, name the source. A withdrawal also changes the package's corpus version, so the old keys could no longer be hit anyway; the purge removes the stored copies of the answers. |
| A1-17 | P1b-03 | Takedown queue with a due date, "10 working days" | `takedown_requested_on` and `takedown_due_on` beside `takedown_reference`; recorded by a reviewer (`record_takedown`, `sources takedown`), separately from the withdrawal, so a request waits on the queue until a reviewer withdraws the source. Working days are Monday to Friday; **public holidays are not counted** (the spec names no calendar). A licence breach we find ourselves is due the day it is recorded. `takedown_queue()` and `TakedownItem.working_days_left()` are for the console's timer (P1b-05). The audit allow-list gains `takedown_reference` and `takedown_due_on` as change fields. |
| A1-18 | P1b-03 | Citations "shown as superseded" in the chat history | The conversation read route returns `superseded` and `withdrawn` per citation; a citation in a live (streamed) answer carries neither, and the web treats a missing flag as false. The citation panel labels the citation "superseded" or "withdrawn" (withdrawn wins) with a one-line explanation. |

**Checks:** ruff and `mypy --strict` clean; `uv run pytest` against a local PostgreSQL 16.15 started in the session container (`TEST_ADMIN_DATABASE_URL`, `REQUIRE_DB_TESTS=1`): 905 passed, 1 deselected (`test_ragflow_integration`); without a database 431 passed, the rest skipped. Web lint, typecheck and 45 unit tests pass; the 8 Playwright tests pass with `PLAYWRIGHT_CHROMIUM_EXECUTABLE` set to the container's Chromium. One full run showed `test_workspace_orchestration::test_cache_misses_when_anything_in_the_key_changes[max_context_tokens]` fail once and pass on every later run; not investigated further (unrelated code).

**Spec questions for the owner:**

1. **Shared canonical links (A1-14).** The spec defines a re-ingestion as a new file at an existing source's canonical link. Where `canonical_url` is a publisher's landing page shared by two documents and only one is ingested, a new, different document at that link replaces it, and the old one is withdrawn. The corpus manifest now says a `canonical_url` must identify one document. Should the match also require the same title (or an explicit "replaces" column in the manifest)?
2. **Excerpts of withdrawn sources (A1-15).** Stored citations of a withdrawn source keep their excerpt in users' history, labelled "withdrawn". For a takedown on licence grounds, should the stored excerpt be blanked as well?

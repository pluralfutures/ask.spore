# Phase 1b Findings

differs from the spec, and why. Metadata only: no query, answer, token, link or email
address is recorded here.

## 1. Where the Group A1 build differs from the spec

Recorded as built, per `CLAUDE.md` ("when the design and the code must diverge, update the
design document"). Migrations 0013 (register states and content roles), 0014 (jobs) and 0015
(withdrawal and re-ingestion).

| # | Item | Spec says | What we did and why |
| --- | --- | --- | --- |
| A1-1 | P1b-01 | `proposed → approved → ingested → withdrawn`, plus `failed` (retryable) | Also **`rejected`**: a reviewer's "reject" (P1b-01 roles, P1b-05 "approve and reject with a note") needs an end state, and `withdrawn` means "removed from the corpus", which a rejected proposal never entered. `failed` is retried by a reviewer (`failed → approved`, `sources retry`), which enqueues a new job. The Phase 0 values go in migration 0013: `registered` becomes `proposed`, an `ingesting` row (an ingestion that never finished) becomes `failed`. Rows ingested before Phase 1b have no proposer or approver; their `approved_at` is their last update, and check constraints require an approval date on every row past `proposed`/`rejected` and a date and reason on every `withdrawn` row. |
| A1-2 | P1b-01 | Register columns listed | Also **`review_note`**: the reviewer's note on an approval or rejection (P1b-05 asks for one). Granted and revoked only from the command line as the schema owner (`ask-spore content-roles grant|revoke --email … --role …`), audited, like the operator role. The application role may only read it, inside the internal tenant's scope; no grant to `askspore_operator` yet: the console pages (P1b-05) decide how they check roles. |

| A1-5 | P1b-01 | "The manifest CLI creates `proposed` rows and, with `--approve-as`, approves them" | Also **`--propose-as`** (the content editor proposing). The same flags (and `--wait`) were added to **`ask-spore ingest` and `ask-spore crawl`**: they were direct paths into RAGFlow, which "no document reaches RAGFlow before a reviewer approves" rules out. | A1-6 | P1b-01 | (re-tagging, P1a-04) | Linking an ingested file into more tags changes which tenants can retrieve it, so it now needs a reviewer too: with `--approve-as` it is approved (`source.retag_approved`, audited with the reviewer) and runs as an `ingest_source` job with `add_tags`; without it the row reports `retag_pending` and nothing is recorded (re-run with `--approve-as`). There is no stored "proposed re-tag". |
| A1-7 | P1b-01 | (not in the spec) | A file whose content hash matches a source **withdrawn after a takedown request** is not proposed again: the row fails with `taken_down`. Otherwise a re-run of the manifest with `--approve-as` would quietly put a taken-down document back. A plainly withdrawn or rejected file can be proposed again (a new row). |
| A1-8 | P1b-02 | Worker reads the file to upload | Every proposed file, **pages included**, is staged under `[files] content_root` by hash at proposal (`app.content.store.stage`), because the worker runs in its own container and a job's payload carries no document contents. P1a-14 said pages are never stored; they are still never downloadable (`stored_path` is set only for PDF, DOCX and PPTX). The staged copy stays after ingestion (re-tags and retries read it) and is deleted on withdrawal. The CLI no longer talks to RAGFlow for ingestion; it needs the database and the content volume only. |
| A1-9 | P1b-02 | `jobs` (type, payload, status, attempts, error_code, timestamps) | Statuses `queued`, `running`, `succeeded`, `failed`. Also `max_attempts` (3), `run_after` (backoff 1, 2, 4 … minutes, capped at an hour), `locked_until` (a 5-minute lease the worker renews while it works; a job whose worker died is claimed again when it lapses) and `created_by`. A check constraint limits the payload to the keys `source_id`, `site_id`, `add_tags`, `downloadable` and `parse_timeout` and caps its size; another limits `error_code` to a short identifier, so no error text can be stored. Only transient RAGFlow failures (timeout, unreachable, HTTP 5xx) are retried automatically; a parse failure or a refusal fails the job at once, and the source is `failed` for a reviewer to retry. A partial unique index allows one queued or running job per type and subject, so an approval enqueues exactly one job, in the approval's own transaction. SIGTERM puts the running job back without counting the attempt. |
| A1-10 | P1b-02 | `crawl_site` job type | The type exists (and `site_id` is an allowed payload key), but the handler is P1b-04's: a `crawl_site` job fails with `unsupported_job_type` until then. The manifest's `site` rows are still crawled by the CLI, and each page goes through the register and the queue like a file. |
| A1-11 | P1b-02 | "the worker does what the P0-09 CLI does today" | Plus: each upload is recorded on the row at once, so a run cut off by a stopped worker leaves a mapping the next attempt deletes from RAGFlow before uploading again. While a source is `approved` and parsing, its chunks can already be retrieved and cited, as an `ingesting` row's could before (`provenance_by_document` excludes only withdrawn sources); unchanged from Phase 1a. An interrupted **re-tag** is not cleaned up this way: its new documents are named in nothing until it succeeds (as before, findings P1a-04). |
| A1-12 | P1b-02 | "The CLI stays as a thin client that enqueues and waits" | Waiting is opt-in with **`--wait`**, so a long manifest can be queued and left to the worker. Without it rows report `proposed`, `retag_pending` or `queued`; with it the final `ingested`, `retagged`, `duplicate` or `failed` (with the job's error code). A row's time in the summary is its submit time plus its job's run time. A `retagged` row reports 0 chunks after `--wait`, because a job records status and error code only. |
| A1-13 | P1b-02 | Worker Compose service | `worker`: the api image with `ask-spore worker`, no published port, on the `app` and `ragflow` networks, with the config and content volumes and Redis (P1b-03 purge). The image's HTTP healthcheck is disabled for it (the CLI run containers of findings 1a §9 showed `unhealthy` for that reason). One job at a time keeps RAGFlow's load as in findings 1a §9 (`MAX_CONCURRENT_TASKS=2` unchanged). Log lines carry `job_id`, `job_type`, `attempts`, `status`, `error_code` (allow-list extended, tested). |
| A1-14 | P1b-03 | Re-ingestion: "new hash, same canonical link" | A proposal whose new file sits at the canonical link of **exactly one** ingested source records `supersedes_id`; once it is ingested, the old source's `withdraw_source` job is enqueued in the same transaction. When several ingested sources share the link, nothing is superseded (the file is a new source). The old row becomes `withdrawn` with the reason "superseded by a re-ingested version" (there is no `superseded` status), and its citations get `superseded_at`, not `withdrawn_at`. **Spec question below.** |
| A1-15 | P1b-03 | Withdrawal cascade | As specified, plus: only an `ingested` or `failed` source can be withdrawn (a proposal has nothing in RAGFlow; an approved one has a job in flight); and the job **deletes our stored copy of the file** unless another live source has the same content, since a takedown for a licence breach should not leave a copy on our disk either. Stored citations keep their excerpt and provenance and are labelled (spec question below). The job runs as a new NOLOGIN role **`askspore_content`** (the app role may `SET LOCAL ROLE` to it, as for `askspore_operator`), because the flags must be set in every tenant's history and the app role is tenant-scoped: it may read only `id`, `tenant_id`, `source_id` and the two flags of `citations` (never the excerpt), update only the flags, and read `tenants.id` (tested). |
| A1-16 | P1b-03 | "purge the tenant answer caches that cite it (cache entries record their source IDs from P1b-03 on)" | Cache values gain `source_ids` (no migration). The purge walks each tenant's `answer:` namespace with `SCAN` through two new `app.core.cache` helpers (`scan`, `delete`, tenant-prefixed like the rest) and deletes entries whose `source_ids`, or for values cached before P1b-03 whose citations, name the source. A withdrawal also changes the package's corpus version, so the old keys could no longer be hit anyway; the purge removes the stored copies of the answers. |
| A1-17 | P1b-03 | Takedown queue with a due date, "10 working days" | `takedown_requested_on` and `takedown_due_on` beside `takedown_reference`; recorded by a reviewer (`record_takedown`, `sources takedown`), separately from the withdrawal, so a request waits on the queue until a reviewer withdraws the source. Working days are Monday to Friday; **public holidays are not counted** (the spec names no calendar). A licence breach we find ourselves is due the day it is recorded. `takedown_queue()` and `TakedownItem.working_days_left()` are for the console's timer (P1b-05). The audit allow-list gains `takedown_reference` and `takedown_due_on` as change fields. |
| A1-18 | P1b-03 | Citations "shown as superseded" in the chat history | The conversation read route returns `superseded` and `withdrawn` per citation; a citation in a live (streamed) answer carries neither, and the web treats a missing flag as false. The citation panel labels the citation "superseded" or "withdrawn" (withdrawn wins) with a one-line explanation. |

**Checks:** ruff and `mypy --strict` clean; `uv run pytest` against a local PostgreSQL 16.15 started in the session container (`TEST_ADMIN_DATABASE_URL`, `REQUIRE_DB_TESTS=1`): 905 passed, 1 deselected (`test_ragflow_integration`); without a database 431 passed, the rest skipped. Web lint, typecheck and 45 unit tests pass; the 8 Playwright tests pass with `PLAYWRIGHT_CHROMIUM_EXECUTABLE` set to the container's Chromium. One full run showed `test_workspace_orchestration::test_cache_misses_when_anything_in_the_key_changes[max_context_tokens]` fail once and pass on every later run; not investigated further (unrelated code).

**Spec questions for the owner:**

1. **Shared canonical links (A1-14).** The spec defines a re-ingestion as a new file at an existing source's canonical link. Where `canonical_url` is a publisher's landing page shared by two documents and only one is ingested, a new, different document at that link replaces it, and the old one is withdrawn. The corpus manifest now says a `canonical_url` must identify one document. Should the match also require the same title (or an explicit "replaces" column in the manifest)?
2. **Excerpts of withdrawn sources (A1-15).** Stored citations of a withdrawn source keep their excerpt in users' history, labelled "withdrawn". For a takedown on licence grounds, should the stored excerpt be blanked as well?

| A2-1 | P1b-03, decision 4 | "A new file at an existing canonical link does not replace the old document automatically … the reviewer chooses replace or keep both" | `propose` no longer sets `supersedes_id`; it reports the ingested sources at the same link (`possible_replacements`), worked out when needed (`replacement_candidates`), so nothing is stored for the flag. A first approval of such a proposal is refused (`replacement_choice_required`) until the reviewer passes `replaces=<one of them>` or `keep_both`; the choice is audited (`replaces`, `keep_both`). With "replace" the A1 supersession path runs unchanged once the new file is ingested. The CLI never chooses: with `--approve-as` the row stays `proposed` (error code `possible_replacement`), and `sources approve --replace <id> \| --keep-both` decides from the shell. The manifest rule that a canonical link identifies one document is gone (corpus-manifest.md). Crawled pages are matched by site and URL instead (P1b-04). |
| A2-2 | P1b-03, decision 5 | "Blanked in stored citations for takedowns on licence grounds … kept, labelled withdrawn, for other withdrawals" | New `sources.takedown_licence_grounds` (migration 0023), set by `record_takedown(licence_grounds=…)`, CLI `--licence-grounds`, and always by `--licence-breach`. The withdrawal job blanks the stored excerpts (`''`) of such a source **and of the earlier versions it replaced** (they carried the same licensed text); every other withdrawal, takedown or not, keeps them. `askspore_content` gets `UPDATE (excerpt)` on `citations`, and a trigger lets that role write only the empty string, so it can blank but never write text; it still cannot read excerpts (tested). The audit event `source.withdrawn` carries `excerpts_blanked`. The chat's citation panel shows "The quoted passage was removed …" in place of an empty excerpt. Answer-cache entries citing the source are purged as before. |
| A2-3 | A1 review note | `propose` staged the file before the role check | The editor role is checked first, inside the proposal's transaction; the file is staged only when a row is recorded, or for an ingested duplicate (a re-tag reads the staged copy, which sources from before P1b-02 lack). A refused proposal leaves no file (tested). |
| A2-4 | A1 review note | `withdraw_source` treated RAGFlow's "not found" on delete as a failure | A failed delete is checked with `get_document`: a document RAGFlow no longer has (or an HTTP 404) counts as deleted and the cascade goes on. RAGFlow v0.27 answers an unknown document with a data error, not a 404, hence the check rather than a code match. |
| A2-5 | P1b-04 | "Sites in a `sites` table: start URL, scope rules, schedule, max pages, per-site allow decision …, last crawl, page count, blocked pages with reasons" | Migration 0024: `sites` (also name, publisher, licence basis and tags for its pages; a review state `proposed → approved` or `rejected` with proposer, approver and note; `special_category_allow`, the reviewer's whitelist; `next_crawl_at`) and **`site_pages`**, one row per page URL a crawl met: `live` (its current register row), `blocked` (reason code, and the special category when that was it) or `removed`. "Blocked pages with reasons" is the `blocked` rows. `sources` gains `site_id`, `snapshot_path` and `fetched_at`. Both tables are operator-owned and outside tenant RLS, like `sources` (no tenant data); the app role may read, insert and update. The allow decision is `allowed`, `robots_disallowed` or `tdm_reserved` (`unchecked` before the first crawl); an unreachable site keeps its last decision and its pages. |
| A2-6 | P1b-04 | "Each crawled page is a register row" and (exit criteria) "nothing reaches RAGFlow before a reviewer approves" | A content editor registers a site; a content reviewer approves it, and **that approval covers its pages**: each crawl records a new or changed page as an `approved` register row in the approver's name (`proposed_by` the site's proposer), audited `source.proposed` and `source.approved` with `method: site_crawl` and the `site_id`, and queues its ingestion. A per-page review on every weekly re-crawl would not be workable. A crawl is refused (`approver_lacks_role`) once the site's approver no longer holds `content_reviewer`. After approval only a reviewer changes the scope, schedule, page budget and whitelist (audited, before and after); tags and licence are fixed (register a new site). Any content role may ask for a crawl now. |
| A2-7 | P1b-04 | "Detects changed pages by hash and re-ingests them, withdraws removed pages" | The hash is the SHA-256 of the rendered Markdown (the raw HTML changes with every nonce or timestamp). A changed page becomes a new register row with `supersedes_id` = the old one, so the A1 supersession path runs (the old version is withdrawn, its citations labelled superseded, once the new one is ingested); this is not the canonical-link matching of decision 4, which is for files. Live pages the walk did not reach are fetched directly: HTTP 404 or 410 → `removed`; a redirect elsewhere → `removed` (`moved`); now out of scope or disallowed → `blocked`; still there → kept (a page budget reached early never removes anything). Every crawl then withdraws the site's register rows that no live page holds, except a version a newer one is still waiting to replace. A page whose register row a reviewer withdrew (e.g. a takedown) is `blocked` (`withdrawn`) and stays out on later crawls; there is no "unblock" yet (backlog). A page whose Markdown matches another source's is `blocked` (`duplicate_content`), one matching a taken-down file `taken_down`. A site that now disallows us or reserves its TDM rights has every live page withdrawn. |
| A2-8 | P1b-04 | "Stores the raw HTML snapshot and fetch date per page under `content_root`" | `snapshots/<sha256>.html` under `[files] content_root` (write-once, by hash, never a URL or title in the path) and `sources.fetched_at` per page version; `site_pages.fetched_at` is the last fetch. The snapshot is deleted with the page's staged Markdown when its register row is withdrawn (unless another live row shares it), like the A1 rule for stored copies. Blocked pages (special-category ones in particular) are never stored. |
| A2-9 | P1b-04 | "Takes publication dates from explicit page metadata only" | `article:published_time`, `og:published_time`, `DC.date(.issued)`, `dcterms.date/issued`, `citation_publication_date`, `citation_date`, `publication_date`, `pubdate`, `date`, `itemprop=datePublished` and JSON-LD `datePublished`; the first ISO date wins. No date in the text, no modification date and no trafilatura guess; otherwise `published_on` stays empty. |
| A2-10 | P1b-04 | "Skips pages matching special-category patterns unless a reviewer whitelists the path" | `app.content.special`: word patterns per category (health, religion, political persons, sexual orientation, ethnic origin, trade union, genetic and biometric, criminal records) matched on the URL path and the page title only, never the text, which would block most policy reports. The list is in code, reviewed in code review. The whitelist is a list of shell-style path patterns per site (`/health/*`), set by a reviewer, audited. |
| A2-11 | P1b-04 | "Rate-limits per host" | One `HostLimiter` per worker process: at least 1 second between requests to the same host (robots.txt and tdmrep.json included), or the site's `Crawl-delay` up to 30 seconds. The worker runs one job at a time, so one crawl runs at a time. |
| A2-12 | P1b-04 | Crawl schedule | The worker queues due crawls between jobs (`schedule_due_crawls`: approved sites with `next_crawl_at` past; the due date moves on at once, so a failing crawl is not re-queued every poll). Weekly is 7 days, monthly 30. Approval queues the first crawl at once. |
| A2-13 | P1b-04 (not in the spec) | Server-side fetches of editor-supplied URLs | The crawler (and the console's URL proposals, P1b-05) fetch only public http(s) addresses on ports 80 and 443: the host must resolve to global addresses only, checked at registration, before each crawl and for every request including redirects (an httpx request hook), so a site cannot point the worker at RAGFlow, PostgreSQL or the cloud metadata address. DNS rebinding between the check and the connection is not covered. |
| A2-14 | P1b-04 | CLI and manifest crawling | `ask-spore crawl` and the manifest's `site` rows now register a site (and approve it, or ask for a crawl now, with `--approve-as`) and the worker crawls it, so there is one crawl path with one policy. `crawl` gains `--name`, `--allow`, `--deny`, `--schedule`; `--out-dir`, `--parse-timeout` (crawl only) and the manifest's `--crawl-dir` are gone (pages are staged under `content_root`). Site rows report `proposed`, `queued`, `ok` or `failed`; with `--wait` the run waits for the crawl and then the pages it queued. The `crawl_site` job's `site_unreachable` is not retried; the next scheduled crawl tries again. Log lines gain `site_id` (allow-list, tested); never a URL or title. |
| A2-15 | P1b-05 | "Operator-side web pages (internal tenant, content roles)" | API under `/api/v1/content` (`app.api.content`), pages under `/content` (register, propose, takedowns, sites, tags; source and site detail), reached by URL like `/operator`. Access is **content roles, not the operator role**: an Authentik-signed-in user of the internal tenant with `content_editor` or `content_reviewer`; anyone else gets 403 on every route (tested for tenant admins, tenant users and internal users without a role). Routes run as the app role inside the internal tenant's scope (users, audit trail, content roles), with the shared register, sites and jobs outside RLS as before. Each action checks its own role in the register and site functions (an editor cannot approve, reject, retry, withdraw, record a takedown, change a site or sync tags: 403, tested); every action is audited there. New audit events: `site.proposed`, `site.approved`, `site.rejected`, `site.settings_changed`, `site.special_category_allow_changed`, `site.crawl_requested`, `site.crawled`, `source.licence_file_set`, `content.datasets_synced`. |
| A2-16 | P1b-05 | "Propose form (file upload or URL …, downloadable flag with the licence basis required when set)" | A multipart form, so the API gains **`python-multipart`** (FastAPI's own form parser; no other change of stack). The licence basis is always required (as in the manifest); a **downloadable** file whose basis is neither `own-work` nor `open-licence` also needs the **permission letter** attached (`licence_file_required`), our reading of "the licence basis required when set" given the P1a-14 rule that third-party files are downloadable "only with the permission recorded per source". A letter can be attached to any source later (editor or reviewer, audited). The uploaded file's name is never stored or logged (the register keeps the hash). A URL proposal is fetched by the API from a public host only (A2-13). A file that is already ingested is reported (`duplicate`, `retag`, `pending`, `taken_down`), not proposed; adding tags to an ingested source stays a CLI step with `--approve-as` (A1-6). Uploads are capped at 100 MB, letters at 20 MB. |
| A2-17 | P1b-05 | "Source detail with history and the licence file; ingestion status and errors" | History is the source's audit trail (event, date, actor's email, status before and after, `site_crawl` for crawled pages), jobs are its last 20 jobs with status and error code. The ingestion error shown is the register's `error` (RAGFlow's parse message, capped at 500 characters): an error message, not document text. No chunk, excerpt or file content is ever returned; a test checks a distinctive sentence of an ingested file appears in no console response. |
| A2-18 | P1b-05 | "A link to the private RAGFlow UI for chunk spot-checks" | `[ragflow] admin_ui_url` (`http://127.0.0.1:8080`, where infra/ragflow publishes the UI) is checked at startup to be an http loopback origin; an operator opens it over an SSH tunnel (`ssh -L 8080:127.0.0.1:8080 <instance>`), as the console page says. The links are built server-side from the register's document IDs and two route templates (`admin_ui_dataset_path`, `admin_ui_document_path`); the defaults are our reading of the RAGFlow v0.27.2 UI routes and **must be checked against the pinned UI** in the release checks (P1b-16). Without `admin_ui_url` the console shows the document IDs only. |
| A2-19 | P1b-05 | "Tag management showing the tag-to-dataset mapping (tags stay in `config/tags.toml`; the page shows and syncs)" | The page lists each tag with its chunking methods, its dataset (or "not synced") and its number of ingested sources. "Sync" is a reviewer's action: the API runs the same server-side `sync_datasets` as `ask-spore datasets sync` (create or adopt a dataset per tag), audited; the file is never edited. No dataset ID is ever taken from a request. |
| A2-20 | P1b-05 | Web tests | Vitest: the helpers (roles, the takedown timer, the proposal form's checks, labels) and the presentational components (register table, source summary and record, replacement choice, propose result, takedown table, site table, site pages, tag table). Playwright (`e2e/content.spec.ts`): no content role is told so; a reviewer filters the register and must choose replace or keep both before approving; an editor sees no review actions. |

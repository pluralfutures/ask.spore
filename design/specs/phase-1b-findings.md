# Phase 1b Findings

Build notes for `phase-1b-build-spec.md`, kept like `phase-1a-findings.md`: where a build
differs from the spec, and why. Metadata only: no query, answer, token, link or email
address is recorded here.

## 1. Where the Group A build differs from the spec

Group A (content operations, P1b-01 to P1b-05) records its rows here.

## 2. Where the Group B build differs from the spec

Group B: client SSO connectors and sign-in hardening, P1b-06 to P1b-08, on branch
`phase-1b/group-b`. Migrations are numbered 0020 onwards on 0012, because Group A1 adds
0013 onwards at the same time; the integration step re-parents 0020 onto Group A1's last
revision (one `down_revision` line).

| # | Item | Spec says | Built |
| --- | --- | --- | --- |
| B1 | P1b-06 | `tenant_login_policy(tenant_id, sign_in_links_enabled, sso_source_kind, sso_source_config, jit_provisioning_enabled, admin_mfa_required)` | As listed, plus `sso_source_slug` (the Authentik source's slug, unique, set exactly when a kind is) and `updated_at` (revision 0020). Forced RLS, `tenant_isolation`, primary key `tenant_id`. The operator role reads, inserts and updates; the pre-authentication role reads the columns discovery needs; the application role reads its own tenant's row and cannot write it. A trigger on `tenants` gives every new tenant its row, so sign-in code requires the row and fails closed without it. `sign_in_links_enabled` is copied from `tenant_entitlements` and the old column dropped; the downgrade moves it back (tested both ways). The operator's switches moved from `PUT …/entitlements` to `PUT /api/v1/operator/tenants/{id}/login-policy`. |
| B2 | P1b-06 | "an unknown domain gets the same neutral response as an unknown user" | Discovery is its own public route, `POST /api/v1/auth/discover`, and is domain-level only: it never reads users, so every address of a domain gets the same answer. The neutral answer (`methods: ["sign_in_link"]`) goes to an unknown domain, a malformed address, a suspended tenant's domain, a domain claimed by two tenants (refused by the console, possible only as the owner) and **a tenant with links off and no SSO**: offering it nothing would tell the caller that the domain is a client's. Its link request is then refused without saying why, as before. A tenant with SSO is necessarily recognisable by its domain; that is what discovery is for (architecture §4.3). |
| B3 | P1b-06 | "the domain resolves to the tenant … and to that tenant's allowed methods" | Discovery decides what the page offers; sending a link still goes by the user, as in P1a-02: a link goes to an invited or active user of an active tenant whose policy has links on, whatever their address's domain (an invited address outside the verified domains, such as the first admin of `cc`, still signs in with links). |
| B4 | P1b-07 | "configures, through Authentik's API, one source per tenant" | Built as specified (`PUT` and `DELETE /api/v1/operator/tenants/{id}/login-policy/sso`, through the provisioner's API token; `app.auth.authentik.configure_source`), and the sign-in round trip is built so that **the browser still never talks to Authentik** (P1a-02's design): the IdP sends the browser back to our public host under Authentik's own callback paths, `/source/oauth/callback/<slug>/` and `/source/saml/<slug>/acs/`; Caddy hands exactly those two paths to the API (`infra/caddy/Caddyfile`), and the API relays them to Authentik on the Compose network with our public host as `Host` (new `[auth.authentik] public_url`), runs the source's flow through the executor API and then the OIDC code flow, as for links. Authentik's pending session for the round trip travels in the starting browser's HttpOnly cookie (path `/source/`, SameSite Lax for OIDC kinds and None for SAML, whose IdP answers with a cross-site POST), never in our database; the database keeps an `sso_attempts` row with the SHA-256 of a binding secret, the tenant and the source (revision 0021: forced RLS, `tenant_id`-first index, pre-authentication role only). **Desk-checked** against the `version-2026.8` source (OAuth redirect and callback views, SAML request and ACS views, source flow manager, property-mapping evaluation), not run live: the live sign-in per connector kind is a release step (P1b-16). |
| B5 | P1b-07 | "The `ask_spore_tenant` attribute is set at provisioning from the source's tenant, never from a claim" | Each source gets a property mapping generated by the API for its tenant (`mapping_expression`, run in the tests as Authentik runs it): the tenant UUID and the verified domains are literals from our database; an address outside them, or a Google `hd` outside them, raises, which makes Authentik refuse the sign-in. It also sets `ask_spore_sso` (source slug, `hd`, address verified, admin-group membership), which the `ask_spore` scope mapping now copies into tokens next to `ask_spore_tenant` (README step 4). **The API checks everything again and is the control the tests prove**: the token's tenant must be the attempt's (resolved from the address's domain when the sign-in started, never from the IdP), its source must be the attempt's source and still the tenant's, the address must be at a verified domain, Google's `hd` must be a verified domain, and the IdP must have verified the address. |
| B6 | P1b-07 | JIT "only when the email domain is verified for that tenant and JIT is on; otherwise … refused unless the user was invited" | As specified, plus: an address that is already a user of another tenant is refused (`email_in_other_tenant`), JIT or not, since an address belongs to one tenant (Phase 1a A8). A JIT user is created active with role `user` (or `tenant_admin` per the Entra group mapping) and the local part of the address as display name: the token carries no name we keep. Source users are separate Authentik users (`user_matching_mode: identifier`, username `<source slug>.<email>`, path `ask-spore/sso`), so an IdP can never take over a sign-in-link user's Authentik account by asserting the same address; both map to the same `users` row by tenant and address. |
| B7 | P1b-07 | "group claims optionally mapped to `tenant_admin`" | The operator lists Entra group object IDs; the user's role then follows membership at **every** SSO sign-in, in both directions, audited as `auth.role_from_sso`. Without listed groups the role is left as the tenant admin set it. Authentik reads Entra groups from Microsoft Graph only with the `GroupMember.Read.All` scope, which the source then requests; Authentik's group sync then also creates the user's Entra groups (IDs and display names) as Authentik groups. **Open for the owner:** accept that, or map from an optional `groups` claim in Entra's ID token instead (a change to the mapping only). |
| B8 | P1b-07 | SAML 2.0 "(metadata upload)" | The operator pastes the IdP's metadata XML; `app.auth.sources.parse_idp_metadata` refuses a document type (so no entity can be declared), more than 256 KB, other than exactly one IdP, an SSO URL that is not public `https`, no HTTP-Redirect binding, and an unreadable certificate. The source sends requests with the HTTP-Redirect binding (a POST binding would need an Authentik page in the browser), wants NameID format `emailAddress`, signed assertions, and no IdP-initiated sign-in. The IdP's certificate is imported into Authentik as a key pair without a private key; the SP signing key pair is generated in Authentik, so no SAML key ever passes through the API. |
| B9 | P1b-07 | "Client secrets and SAML keys are stored in Authentik only" | The secret is a write-only field of the console's request (`SecretStr`), passed to Authentik and never stored, returned, audited or logged; tested against the policy row, the audit rows, the response and stdout. The audit event `operator.sso_source_changed` carries the kind, the source slug and a SHA-256 of the stored non-secret configuration. A new source or a change of kind needs the secret; saving the same kind without it keeps Authentik's. Generic OIDC issuers must be public `https` names (no IP literal, port or credentials), since Authentik fetches their well-known document. |
| B10 | P1b-07 | "the tenant admin page shows the configured source read-only" | `GET /api/v1/admin/login-policy` and a "Sign-in" section on the tenant admin page: the policy's switches, the non-secret source fields and the endpoints the client's IT registered; no route changes it. A failed SSO sign-in returns to the sign-in page with a generic message; the reason is in the audit trail only (`auth.login_failed`, method `sso`, error code). |
| B11 | P1b-08 | "Per-IP rate limit on `POST /auth/link` at the API (Caddy's limit as a second layer)" | At the API, per route and client IP, a sliding window (`[auth] ip_requests_per_window = 10` per `ip_window_seconds = 600`), applied to `POST /auth/link` and also to the other two public pre-authentication routes, discovery and SSO start, each counted on its own. Over the limit: 429 `rate_limited` with `Retry-After`, before anything else (no lookup, no binding cookie, no row, no email). The client IP is the last `X-Forwarded-For` entry (Caddy sets it to the connecting address) or the socket peer; only its SHA-256 is held, in memory, per API process; the address is never logged. **Caddy's layer is not built:** the official `caddy` image has no rate-limit module, and adding one means a custom Caddy build, which is a stack change for the owner to decide (Stack Decision); the API's limit stands on its own meanwhile. |
| B12 | P1b-08 | "the landing page's `no_binding` message made explicit" | `POST /auth/link/complete` now answers `no_binding` (instead of the generic `sign_in_failed`) when the request carries no binding cookie, which is decided before anything is looked up, so it reveals nothing about the address; every other refusal stays generic. The landing page then says: "Open this link in the same browser window where you asked for it." A second POST from the browser that already signed in also gets it, since success clears that browser's binding cookie. The sign-in page says when the network is rate limited. |
| B13 | P1b-08 | "session refresh before the access token expires (provider validity 8 hours)" | The API now asks for `offline_access` and keeps Authentik's refresh token in its own cookie `askspore_refresh` (HttpOnly, Secure, SameSite=Strict, path `/api/v1/auth`, so only the refresh and sign-out routes see it; 24 hours, `[auth] refresh_token_ttl_seconds`, matching the provider's `refresh_token_validity`). `GET /me` gains `session_expires_at`; the web app calls `POST /api/v1/auth/refresh` five minutes before it. The refresh grant rotates the refresh token at Authentik, and the API also lists the spent refresh token and the previous access token in `revoked_sessions`, so neither works again even if Authentik's rotation failed (tested); the new token must name the same user, still active. A session therefore lasts while the user keeps the app open, at most 24 hours past its last renewal; whether a session needs an absolute cap (re-authentication every N days) is **open for the owner**. The provider needs the `refresh_token` grant type (README step 5, blueprint). |
| B14 | P1b-08 | "the Authentik access token revoked on sign-out, verified live" | Sign-out now revokes the refresh token too: both are listed in `revoked_sessions` and revoked at Authentik (RFC 7009, with the matching `token_type_hint`); the refresh route refuses a listed refresh token whatever Authentik answers, and revokes again whatever Authentik issued for it. Tested against the fake provider, including one that ignores the revocation. **Not verified live** here (no Authentik in this build): the live check is a release step, as for A7 and D1. |
| B15 | P1b-08 | "MFA requirement for tenant admins enforced through an Authentik authenticator validation stage bound to the admin group" | Built as specified, with three consequences of the API running the flow (P1a-02): (1) **relay**: the validation stage (TOTP only; enrolment through a TOTP setup stage the first time) is bound in the sign-in-link flow to group `ask-spore-tenant-admins`; when Authentik stops at it, `POST /auth/link/complete` answers 200 `mfa_required` (with the `otpauth://` URI for enrolment, `Cache-Control: no-store`) and the browser POSTs the code to `POST /api/v1/auth/mfa`, bound to that browser by a new `mfa_challenges` row (revision 0022: forced RLS, `tenant_id`-first index, pre-authentication role only; at most 5 codes in 5 minutes). Authentik's pending session travels in the browser's cookie. WebAuthn and hardware keys cannot be relayed this way, so only TOTP is offered; README step 9's "hardware key for operators" cannot work with the API-run flow either and **needs an owner decision** (operators are `user` role, so this build does not challenge them). (2) **group membership is the API's**: it adds a tenant admin to the group when invited (operator or tenant admin), moves users in and out when their role changes, and moves all of a tenant's admins when the operator switches `admin_mfa_required` (nothing is saved unless Authentik took every change). (3) **fail closed**: a tenant admin of a tenant that requires it who completes a link flow without the second factor is refused (`mfa_not_enforced`), the tokens Authentik issued are revoked, and the admin is put in the group, so their next link asks for it. This also covers admins invited before this release, such as `cc`'s first admin: their first link after the release is refused once, the next asks them to enrol. The second factor applies to sign-in links; reading architecture §4.3 ("tenant admins must use SSO or sign-in link plus a second factor") as SSO admins relying on their own IdP's MFA, which the client's IT sets (onboarding pack, P1b-09). The enrolment page shows the key as text and an `otpauth://` link, without a QR code (no new web dependency). |
